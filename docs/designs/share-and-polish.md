# Design: QA pass, layout links, and a friendlier look

Generated by /office-hours on 2026-10-31
Branch: main
Repo: raduuuuu/ChooChooCAD
Status: APPROVED
Mode: Builder

## Problem Statement

ChooChooCAD can design, check, view in 3D and walk a wooden-railway layout
piece by piece on the floor. But a layout lives only in one browser's
localStorage, so nobody else can see it. The app also "looks like a tool, not
a toy", its verdict area is heavy, and a first visit doesn't make clear what to
do. Nobody has run a QA pass across the whole current version on phones and
tablets. Separately, the printable build sheet (PR #88) repeats what build mode
already does, so it goes.

## What Makes This Cool

A friend opens a link and sees your railway: the plan, the verdict, the parts
list, a 3D view. One tap on Build it walks them through it on the floor. They
can open it in their own editor, change it and send their version back. No
accounts, no server, no gallery. The layout travels inside the link.

## Constraints

- Static site on GitHub Pages. No server, no accounts, no analytics backend.
- The main chunk budget is 134.02 kB (`scripts/chunkBudget.ts`). Sharing code
  that only the recipient needs goes in a lazy chunk.
- DESIGN.md governs the look. Colour carries meaning only on verdicts (rule 2).
  Warmth comes from type, space, wood tones already in the tokens and copy,
  not from new colours on chrome.
- Opening a link must never change the recipient's saved layout. Today
  `loadGraph` (`app/src/layoutStore.ts:305`) reads localStorage itself, and
  `rescue()` (`:152`) writes the rescue slot. Neither may run for a link.
- Every test pin records a mutation that was actually run, and quotes its real
  failure message (repo convention).

## Premises

1. Sharing is a link that opens a read-only view of the layout: 2D plan (3D on
   request), the verdict and the parts list, plus Build it and Open in editor.
   Open in editor never silently overwrites the friend's own layout.
2. No server. The layout is encoded in the link's fragment (`#…`), which never
   reaches GitHub Pages' logs.
3. The printable sheet is removed: `BuildSheet.tsx`, `sheetLayout.ts`, their
   tests, the print CSS, `--sheet-paper`, every "Print the sheet" button, the
   `printOnly`/`printing` paths in build mode, and the DESIGN.md sheet bullet.
   `segmentMid` stays if anything else still uses it. The build-step engine
   stays.
4. The look work stays within DESIGN.md. It adds warmth, a lighter verdict area
   and a clear first visit, and it is designed and reviewed before it is built.
5. Order: QA first on the current version, then the sheet removal, sharing and
   the look, then a final QA pass.

## Cross-Model Perspective

Codex, in a cold read:
- **Coolest version:** "a playable building invitation". The link leads to
  building together on the floor, and the friend sends their version back.
  The first visit is a ready-to-build example with "Build this" and "Make your
  own".
- **Key insight:** the user switched from "a public gallery" to "A friend opens
  a link". What they want is someone else building their creation.
- **Existing tool:** lz-string covers the link transport. Everything else is
  ours to build: a versioned format, bounded decoding, read-only routing,
  editor isolation, the recipient screen.
- **Risks:**
  - High: a storage-aware loader could change the recipient's saved work.
  - High: hostile or oversized payloads.
  - Medium: messaging apps may truncate long links. Measure it, and offer a
    file fallback.
  - Medium: versioning, and recomputing the verdict instead of trusting one
    in the link.

Where we landed:
- Taken: both High risks (they are why the decoder must be pure), versioning,
  the recomputed verdict, and the example on first visit.
- Not taken: lz-string. Native `CompressionStream('deflate-raw')` adds no
  dependency. The compact encoding matters more than the compressor.
- Comes for free: "Send your version back" is Open in editor followed by Share.

## Approaches Considered

### Approach A: Minimal
QA, the sheet removal and the share link, with look work only on the
recipient screen. Rejected: the editor would still look like a tool, and its
verdict would stay heavy.

### Approach B: Full (chosen)
QA and fixes, the sheet removal, a versioned link with a pure decoder and a
read-only view, then an editor look redesign that is designed first, then a
final QA pass.

### Approach C: Invitation-first
B, but the recipient screen leads with Build this and a "what you're missing"
list. Not chosen: more new UI before the editor's look gets any attention.

## Recommended Approach

Approach B, in this order:

1. **QA baseline (live site).** Cover every flow: empty state, presets,
   placing, joins, undo, 2D/3D, build mode, save/reload. Test on desktop, on a
   tablet (portrait and landscape) and on a phone. Include odd layouts: big,
   two-level, switches, other brands, a corrupt save, a full storage. Fix bugs
   with a test each. Write deferred findings to TODOs.
2. **Remove the printable sheet** (premise 3). This is a deletion PR. The
   chunk budget is re-checked and re-baselined if it drops a lot.
3. **Share link.**
   - Format: `#v1.<base64url(deflate-raw(compact))>`. `compact` lists part
     codes, turns, welds and anchors in a fixed order. It is not the stored
     JSON. The version prefix lets later formats coexist.
   - Part codes: an explicit table (`shareCodes.ts`) that only ever grows.
     A code is never reused or reordered, and a removed part keeps its code
     reserved. One test pins the existing codes. Another test fails when a
     built-in part has no code. Codes are never catalogue indices.
   - Decoder: pure, and it refuses anything that is not fully valid. It never
     repairs: no dropped anchors, no re-placing, no legacy migration.
     - The checker is extracted from `loadGraph` as a pure function over the
       parsed graph, and both paths call it.
     - `loadGraph` keeps everything else: the storage reads, the legacy
       migration, the repairs and `rescue()`.
     - A test spies on `localStorage.setItem` and proves the decoder path
       never calls it.
   - Caps, enforced before anything is solved:
     - fragment length: 32,768 characters
     - inflated size: 256 KB
     - pieces: 2,000
     - These are starting values. Eng review checks them against the largest
       corpus layout, with headroom.
     - Inflation reads the `DecompressionStream` in chunks and stops the
       moment the inflated-size cap is passed. A test covers a high-ratio
       payload (1 MB of zeros).
     - An unknown part code or an unsupported version is refused.
   - The verdict is recomputed on arrival. Nothing in the link claims
     "buildable".
   - Sender side: a Share button copies the link (or opens the Web Share
     sheet on touch devices). It reports the link's length. Over a stated
     limit, it offers a downloaded layout file instead.
   - Layout file: a `.choochoo` text file holding the same `v1.…` string.
     The recipient opens it with "Open a layout file" in the editor (a file
     picker), or by dropping it on the canvas.
     - It opens the same read-only view as a link, with Build it, Open in
       editor and Back to my layout. It never loads straight into the editor.
     - Opening it flushes the editor's pending save and suspends autosave,
       exactly as `hashchange` does.
     - Its exits follow the link's exits. There is just no fragment to
       clear.
     - It goes through the same decoder and caps. The bad-input tests and the
       storage isolation test both include a file case.
   - Routing:
     - On load, the fragment is checked before `loadGraph` runs. A `#v1.` link
       mounts the read-only view and never calls `loadGraph`.
     - The editor's autosave is suspended while the link view is mounted
       (`savesSuppressed`).
     - A link pasted into an open tab arrives as `hashchange`. The editor's
       pending save is flushed first, then the link view opens with the same
       isolation.
     - Every exit clears the fragment with `history.replaceState`: Open in
       editor, the bad-link exit, and Back to my layout. A reload then shows
       the editor.
     - Tests cover a reload after Open in editor and a `hashchange`.
   - Storage, in a link session:
     - It may write one key only: `brio.build.link.v0`, the build progress of
       the link being built. This is a single slot, keyed by `layoutKey`, so
       the next link replaces it. Nothing piles up.
     - It never writes the saved layout, the rescue slot, the recipient's own
       build progress (`brio.build.v0`), the view mode, the inventory or the
       table.
     - The success-criteria test snapshots every key, opens a link, runs
       Build it for a few steps and exits. Then it compares every key except
       `brio.build.link.v0`.
   - Open in editor:
     - If the recipient's saved layout is empty, the link replaces it.
     - Otherwise the saved layout is first written to a put-aside slot,
       `brio.graph.v1.previous`. It is separate from the rescue slot.
     - The slot is read back and compared byte for byte before the link's
       layout replaces the saved one. If the write or the check fails (for
       example, full storage), nothing changes, and one sentence says the
       layout couldn't be put aside.
     - If the put-aside slot already holds a different layout, Open in editor
       asks first: replacing it is a choice, never silent. If it holds the
       same layout, there is nothing to ask.
     - The editor starts a fresh undo history.
     - Instead of a short-lived Undo, the editor shows "Restore my previous
       layout" for as long as the put-aside slot is filled. Restoring swaps
       the two, so it is reversible.
     - The swap loses nothing:
       - It reads both layouts into memory.
       - It writes the put-aside slot first and checks it, then writes the
         saved layout and checks that.
       - If any write fails, it writes back whatever was overwritten from the
         in-memory copies and shows one sentence. The editor keeps showing
         the layout it showed before.
     - Tests cover an empty saved layout, two Open in editor actions in a
       row, full storage on Open in editor, and full storage on Restore.
   - A bad link gets one plain sentence and a way into the editor. It never
     gives a blank page.
4. **Look redesign.** Run /design-consultation or /plan-design-review on three
   things:
   - warmth within DESIGN.md
   - a lighter verdict area: one line, with details on request
   - the first visit: a built-in example the user can build, or start their
     own
   Then build it in small PRs.
5. **Final QA pass** over the changed flows, on the same devices.

## Open Questions

- Real link lengths. Encode the presets and the largest corpus layouts,
  measure them, and pick the "use a file instead" threshold from data. The
  ~2 KB messaging limit is a guess until tested in real apps.
- Whether one put-aside slot is enough, or a short list of past layouts is
  worth it. Eng review decides. The one-slot rules above are the default.
- Whether the read-only view shows the 3D view first on touch devices. Design
  review decides.
- Custom parts in a shared layout. The TODO "`dimensions.status` is a
  self-asserted claim, which blocks sharing" stands. v1 shares built-in parts
  only, and a layout that uses a custom part says so instead of making a link.

## Success Criteria

- A link made on one device opens on another, in a browser that holds a
  different layout. It shows the same plan, verdict and parts list. The
  recipient's own layout is byte-identical afterwards. A test checks this.
- A corrupt, truncated, oversized or future-version link shows one sentence
  and an exit. It never crashes, and it never writes storage. Tests cover each
  case.
- The Stadium preset's link fits in a chat message. Its measured length is
  written in the PR.
- No "Print the sheet" anywhere. The build-mode tests still pass.
- QA: every flow listed in step 1 is exercised on desktop, tablet and phone.
  Each bug found is fixed with a test or filed.
- The look work is approved in a design review before code, and it passes
  /design-review after.
- The main chunk stays under budget.

## Distribution Plan

Pages deploys woodentrain.world on merge to main. Links use the site's own
origin, so nothing new is hosted.

No blocking findings remain. The 11 open minor finding(s) below are recorded for the user, not fixed.

### R3-1 — clarity (minor)

**Problem**

> Persisting R2-3: the document still does not say what happens when the recipient declines to replace a put-aside slot that holds a different layout.

**Remedy**

> State that declining leaves both the saved layout and the put-aside slot untouched and returns to the read-only view.

### R3-2 — completeness (minor)

**Problem**

> Persisting R2-4: Restore swaps the two layouts, so the put-aside slot is never emptied and 'Restore my previous layout' stays on screen permanently once a link has been opened in the editor. There is no way to dismiss it or clear the slot.

**Remedy**

> Add a way to dismiss the entry or discard the put-aside layout, with a confirmation, or leave its presentation to design review as an explicit open question.

### R3-3 — completeness (minor)

**Problem**

> Persisting R2-5: a removed part keeps a reserved code, but the document does not say what an old link using that code shows. 'An unknown part code ... is refused' may or may not cover a reserved code.

**Remedy**

> State that a reserved code is refused with the bad-link sentence (or a specific 'this link uses a part that no longer exists' sentence), and add it to the bad-input tests.

### R3-4 — feasibility (minor)

**Problem**

> Persisting R2-6: the layout file goes through the same caps, including the 32,768-character fragment cap, so a layout too large for a link is also too large for the file fallback. The sender side still does not say what Share does when the encoded layout exceeds the caps.

**Remedy**

> Have Share check the encoded length against the decoder caps and say plainly that the layout is too large to share, instead of producing a link or file that will be refused. Eng review can confirm the cap leaves headroom over the largest corpus layout.

### R3-5 — clarity (minor)

**Problem**

> Persisting R2-7: 'If the recipient's saved layout is empty, the link replaces it' still does not define empty (no stored key, an empty graph, or a corrupt save). A corrupt save or a filled rescue slot could be treated as empty and replaced without a put-aside copy.

**Remedy**

> Define empty as a valid stored layout with no pieces, or no stored layout at all with no rescue or legacy data. Anything else takes the put-aside path.

### R3-6 — clarity (minor)

**Problem**

> Persisting R2-8: the success criterion 'The Stadium preset's link fits in a chat message' is still untestable as written, since Open Questions concedes the ~2 KB limit is a guess and no app or limit is named.

**Remedy**

> Restate the criterion against the measured threshold, for example: 'the Stadium link is under the measured threshold N and opens intact when sent through the apps that were tested'.

### R3-7 — clarity (minor)

**Problem**

> Persisting R2-9: on touch devices, the document still does not say when the link length is reported or the over-limit file offer appears relative to the Web Share sheet, nor what happens when Web Share is unavailable or cancelled.

**Remedy**

> Specify the order: check the length first, then offer the file over the limit or share or copy under it. Fall back to copying when Web Share is unavailable, and treat a cancelled sheet as a no-op.

### R3-8 — clarity (minor)

**Problem**

> Persisting R2-10: step 2 still says the chunk budget is 're-baselined if it drops a lot', with no threshold or owner.

**Remedy**

> State the rule, for example: re-measure after the deletion, and re-baseline only if it drops by more than X kB, with the owner's approval, recorded in chunkBudget.ts.

### R3-9 — scope (minor)

**Problem**

> Persisting R2-11: the first-visit built-in example in step 4 still has no storage behaviour. The document does not say whether loading it writes the saved layout, or how a first visit is detected without overwriting an existing user's layout.

**Remedy**

> State that the example is shown only when there is no saved layout (and no legacy or rescue data), and that it is not persisted until the user edits it or chooses 'Make your own'. Leave the visual treatment to design review.

### R3-10 — clarity (minor)

### R3-11 — completeness (minor)

**Problem**

> The new swap order overwrites the put-aside slot first, so between the two writes the previous put-aside layout exists only in memory. The two writes are synchronous in one task, so the window is tiny (a browser crash or power loss), but the rollback rule also does not say what happens if the restoring write itself fails.

**Remedy**

> Optionally note that the two writes run in one synchronous task, or stage the incoming layout in a temporary key first. State that if the rollback write fails, the in-memory copy stays on screen with a sentence asking the user to keep the tab open or share the layout.
