## 0A. Premise challenge

- **Real problem:** a parent with a box of track wants to know "can I build this, and
  if not, what exactly do I buy?" and "what can I build from what I have?".
- **Sets were a proxy** for fast data entry. Dropping them removes the provenance risk
  the P2 itself named ("a second body of transcribed third-party data") and the maker
  naming problem (no brand names in copy). Counting per part is slower to enter; the
  quick-fills and a "count this layout" shortcut can close that gap.
- **"Rebuild with what I have"** in the old P2 is ambiguous: it can mean (a) which
  ready layouts can I build from my box, or (b) the app designs a new layout from my
  box. (a) is a filter; (b) is a search over layouts with the closure solver, a much
  larger job.
- **Do-nothing cost:** the shortfall line already names missing parts, so the user can
  copy them by hand. Low pain for the buy list; the real gap is (a).

## Landscape (search, 2026-11-05)

- Brick-toy apps answer "what can I build" with a list of known models matched against
  your parts, often as a percentage, and some link to buying missing pieces
  (emagineer: "every official set you can build with the bricks you already own";
  Brickit scans a photo and suggests builds). Reviews ask for "only the ones I have
  every piece for". [apps.apple.com/us/app/id6739147739]
- Layer 3: a track layout is far smaller than a brick model, and the app already has
  a solver that says whether a loop closes. A match list over ready layouts is cheap;
  generating new closed layouts from a box is the differentiating 10x, and the solver
  makes it possible where brick apps cannot.

Header: Inventory
A) Buy list + what fits (recommended)
A "Copy buy list" that lists exactly what to buy for this layout, plus a "What can I build" list that checks every ready layout against your box and says which you can build now and what the rest are short of. Effort M (human ~2 days / CC ~1h), risk low, all pure code over existing counts. ✅ Answers both questions a parent asks with no new data. ✅ Reuses the shortfall maths and the presets. ❌ Only three ready layouts exist today, so the list is short until more are added.
B) Buy list only
Just the copyable buy list next to the shortfall line. Effort S (human ~3h / CC ~20m), risk low. ✅ The smallest change that closes the P2's named gap. ✅ No new screen or list to design. ❌ Leaves "what can I build with my box" unanswered, the half the landscape apps lead with.
C) Also design layouts for me
A, plus the app searches for new closed layouts using only the parts you own and offers the best few. Effort XL (human ~2 weeks / CC ~1 day), risk high. ✅ The 10x answer: no brick app can promise a layout that closes. ✅ Uses the solver this app already trusts. ❌ A new search engine with its own speed, quality and "why this one" problems.

1. **Architecture:** no new module. Inventory.tsx loses markup; inventoryModel.ts loses
   QUICK_FILLS; App.tsx moves one button out of the D10 gate. Storage key and format
   unchanged, so a stored box loads as before.
2. **Errors and rescue:** unchanged paths. The count guard (`sanitizeCount`, "needs a
   number"), the discard notice on a bad blob, and the save-failure notice all stay.
3. **Security and privacy:** nothing leaves the browser; counts stay in localStorage.
4. **Data flow and edge cases:** empty canvas with the panel open: every row shows
   "in use" blank; undeclared stays null until a number is typed; Forget this returns
   to undeclared. A stored box with quick-fill counts keeps them (they were only counts).
5. **Code quality:** dead code removed with the feature (QUICK_FILLS and its tests),
   not left behind.
6. **Tests:** the quick-fill tests go with the quick-fills. New: a DOM test that Your
   box is offered on an empty canvas and the panel holds only rows, no quick-fills;
   the existing socketAdapter test that drives a quick-fill is rewritten to type counts.
7. **Performance:** less DOM. No change.
8. **Observability:** `action/your-box` already counts opens (PR #150).
9. **Deployment and rollback:** one PR; revert restores the panel. No migration.
10. **Long-term:** the deferred buy list and what-fits build on the same counts.
11. **Design:** the panel becomes a plain form. The empty-state line must not use
    above/below/left/right wording (DESIGN.md rule 7) and names no maker.
